## 1. 产品概述

### 1.1 定位

Cashflow 是一款只做移动端的个人记账应用，围绕四件事展开：**快速记账**、**文本批量导入**、**收支分析与可视化**，以及**登录后的账单云端同步**（数据存储在 Neon Postgres，多台设备数据一致）。

参考项目中，移动端开源记账 App（Cashew、My Expenses、Financisto）的导入能力主要是 CSV / QIF 文件，flow 则主要通过 URI 添加记录；自托管项目（ezBookkeeping）的导入能力更强，但需要自行部署。轻量的文本格式导入仍有空间，Cashflow 把它作为核心能力之一。

### 1.2 目标用户

- 想用几秒钟记完每一笔收支、不想被复杂功能打扰的个人用户
- 有历史账单（表格、备忘录、其他 App 导出的数据）需要迁移的用户
- 想清楚知道「钱花在哪、有没有超支」的上班族、学生和小家庭
- 有多台手机或换机需求，希望账单跟着账号走的用户

### 1.3 设计原则

1. **移动优先**：竖屏单手操作，核心操作位于底部
2. **本地优先**：数据先写入本机，离线可用；登录后在后台同步到云端
3. **输入速度优先**：常用记账路径越短越好
4. **统计口径透明**：转账、日期、结余的计算规则在界面和文档中保持一致

### 1.4 MVP 范围（v0.1）

| 包含 | 不包含 |
|---|---|
| 手机浏览器 / 已安装的 PWA，竖屏为主 | 桌面端专属布局、平板适配 |
| 单用户、本地优先 + 登录后云端同步、单币种（CNY） | 多人共享、家庭账本 |
| 收入 / 支出 / 转账，账户与分类 | 银行直连、自动抓取账单、投资持仓 |
| 收支汇总、分类占比、近 6 个月收支 | 资产负债表、税务报表 |
| 文本导入、JSON / CSV 导出、JSON 恢复 | 微信 / 支付宝账单适配（见第 12 章） |
| 邮箱验证码登录、多设备同步、账号注销 | 手机号登录、第三方 OAuth 登录（见第 12 章） |

### 1.5 成功指标（建议）

- 常用支出（默认账户 + 历史分类）平均记账耗时 ≤ 10 秒
- 500 行合规文本的解析预览 ≤ 2 秒；有效行导入成功率 100%
- 备份导出后再恢复，数据逐条一致，零丢失
- 登录后，两台在线设备之间的数据同步延迟 ≤ 10 秒
- 断网记账的数据 100% 保存在本机，恢复网络后自动上传，且不产生重复记录

文本格式参考（借鉴思路，不引入代码）：
- [Beancount](https://beancount.github.io/) / [hledger](https://hledger.org/)：纯文本复式记账，「日期 + 描述 + 金额 + 账户」的文本语法。我们借鉴其思路，但为移动端输入简化为单行格式
- [MoneyMatter](https://moneymatter.app/)：支持粘贴银行账单或邮件，由 AI 解析为交易记录。作为 P2 参考

### 2.2 共性经验（已采纳）

1. 账户、分类、记录是通用骨架；转账作为账户间的资金移动单独建模（Financisto、My Expenses 均支持账户间转账），且本产品规定转账不计入收支
2. 导入需要列映射与预览确认，错误行必须可见（ezBookkeeping 的列映射与规则是典型做法）
3. **本地优先 + 完整备份** 是开源记账 App 的共同卖点（flow、Actual Budget、Financisto）
4. 统计的基础是 **分类占比 + 时间趋势**，自定义维度属于进阶功能（My Expenses、ezBookkeeping）
5. **输入速度决定留存**：历史分类记忆（Cashew）、桌面快捷入口（My Expenses）、URI 快速记账（flow）

### 2.3 许可证注意事项

- Cashew、flow、Financisto、My Expenses 为 GPL 协议：**只借鉴设计与交互思路，不复制代码**，除非 Cashflow 同样以 GPL 开源
- ezBookkeeping、Actual Budget 为 MIT：复用代码时保留版权声明即可

## 3. 术语

| 术语 | 定义 |
|---|---|
| 记录 | 一笔收入、支出或转账，是最小数据单元 |
| 账户 | 资金所在位置，如现金、储蓄卡、信用卡、电子钱包 |
| 分类 | 收支用途，两级结构，如 `餐饮 / 午饭` |
| 转账 | 账户之间的资金移动，不计入收入或支出 |
| 结余 | 收入 − 支出（不含转账） |
| 导入批次 | 一次导入产生的全部记录，可整批撤销 |
| 本机模式 | 未登录时的使用方式，数据只保存在本机 |
| 待同步队列（outbox） | 本机尚未上传到云端的变更列表 |

### 6.5 文本导入（IMP）【核心功能】

#### 6.5.1 流程

1. 进入导入页。应用**不内置任何解析格式**：没有「解析脚本」时不能解析文本。
2. 获得脚本的两种方式：
   - **生成脚本**页签：粘贴账单文本 → 复制提示词 → 交给任意 AI 生成脚本 → 把返回的脚本粘贴回来保存为规则（自动去掉 ```` ```js ```` 围栏）；
   - **新建脚本**：自己写一段 JS 函数体。
3. 回到**导入**页签，粘贴文本或选择 `.txt` / `.csv` 文件，点击「解析预览」。
4. 脚本在沙箱中逐行执行并生成预览；用户处理需确认的行（补类型、映射分类/账户、决定是否保留疑似重复）。
5. 点击「导入」，显示结果：成功 N 条、跳过 M 条、失败 K 条。
6. 在导入历史中可撤销整个批次。

预览状态：

- ✅ **可导入**：解析成功，分类和账户均已匹配
- ⚠️ **需确认**：分类或账户不存在、类型缺失、疑似重复（默认跳过）
- ❌ **错误**：脚本报错或缺少必填字段（默认不导入）

#### 6.5.2 解析脚本（替代 v0.2 的固定格式 A）

脚本是一段**函数体**，App 用 `new Function("line", "ctx", "index", script)` 包装后逐行调用。

| 参数 | 说明 |
|---|---|
| `line` | 当前行原始文本（全角符号已转半角） |
| `ctx.accounts` | `{ id, name }[]`，当前可用账户 |
| `ctx.categories` | `{ id, name, kind, parentId }[]`，当前分类树 |
| `ctx.defaultAccountId` | 默认账户 id 或 null |
| `ctx.today` | 今天日期，`YYYY-MM-DD` |
| `index` | 当前行下标（从 0 开始） |

| 返回字段 | 必填 | 说明 |
|---|---|---|
| `date` | 是 | `YYYY-MM-DD`；只有月日时用 `ctx.today` 补年份 |
| `amount` | 是 | 正数，单位**元**；支持 `"1,234.50"`、`"¥35"`、`"35元"` |
| `kind` | 否 | `income` / `expense` / `transfer`，缺省时按分类推断 |
| `category` / `categoryId` | 否 | 分类名（可写「一级/二级」）或分类 id；**必须是账本里已有的分类**，拿不准写「其他」 |
| `account` / `accountId` | 否 | 账户名或 id；**必须是账本里已有的账户**，转账写「转出>转入」且两端都要有 |
| `toAccount` / `toAccountId` | 否 | 转入账户（转账） |
| `note` / `tags` | 否 | 备注与标签；备注里的 `#标签` 会自动提取 |
| `time` | 否 | `HH:mm` |

- 返回对象 = 一条记录；返回 `null` / `undefined` = 跳过该行（表头、分隔线、合计行等）。
- **可导入的硬性条件**：非转账行必须有能匹配到的分类，转账行必须有「转出>转入」两个账户；不满足的行停在「需确认」，无法直接导入（转账缺转入账户时预览里没有补救入口）。
- 运行时限制：没有 DOM、网络、localStorage / IndexedDB；禁止 `import` / `require` / `async`；超过 **3 秒**强制终止；单次最多 2000 行。
- 安全：脚本在 `sandbox="allow-scripts"`（无 `allow-same-origin`）的 iframe 中执行，拿不到账本数据、本机存储与登录态；**脚本规则只保存在本机，不参与云端同步，也不会在服务端执行**。
- 规则可配置：首行表头跳过、注释前缀、日期写法、分类层级分隔符、转账账户分隔符。
- 金额单位：脚本用「元」，服务端与本地库统一存「分」，由应用换算。

示例：

```js
// 2026-10-02 | 支出 | 35.5 | 餐饮/午饭 | 微信 | 公司楼下 #工作
const cells = line.split("|").map((s) => s.trim());
if (cells.length < 3) return null;

const amount = Number(cells[2].replace(/[^\d.]/g, ""));
if (!amount) return null;

return {
  date: cells[0],
  kind: cells[1] === "收入" ? "income" : cells[1] === "转账" ? "transfer" : "expense",
  amount,
  category: cells[3],
  account: cells[4],
  note: cells[5],
};
```

#### 6.5.3 生成脚本提示词

「生成脚本」页签把三段内容拼成一段可复制的提示词：

1. **系统提示词**：脚本契约（运行方式、参数、返回字段、**可导入的硬性条件**、解析要求、输出前自检、两个示例——分隔符文本与银行短信）；
2. **当前账本**：账户名、分类树与今天日期，让 AI 直接映射到已有账户与分类；
3. **账单文本**：用户粘贴的样例（建议 5–20 行有代表性的内容）。

提示词里明确要求：分类只能取账本里已有的（拿不准写「其他」），转账两端不齐就退回支出——避免 AI 生成「分类缺失 / 转账缺转入账户」这类需要逐行手补的脚本。

复制后交给任意 AI，把返回的脚本整段粘贴回来即可保存为规则并跳转到导入页。

#### 6.5.4 重复与映射

- **疑似重复**：与已有记录的日期、类型、金额、账户完全一致，或与本次文本中前面的行完全一致，默认跳过，可手动勾选保留
- **分类或账户不存在**：可在预览里逐行映射到已有项，或新建（新建的分类默认为一级分类）
- **脚本没有给出的字段**：类型用下拉补齐，分类用下拉选择，账户落到默认账户并在预览中标注
- **分类是兜底「其他」**：预览顶部提示行数，并在该行露出分类下拉（不阻断导入）；用户指定后按「规范化商户名 → 分类」记在本机，下次解析自动套用，行上标注「分类按记忆套用」（IMP-09，本机存储、不参与云端同步）
- 账户映射仍只对本次导入生效

  imported: number

- 转账只存一条记录，不拆成两条收支，避免重复计算
- 统计只计入 `deletedAt` 为空的记录
- 所有需要同步的实体都带 `createdAt`、`updatedAt`、`deletedAt`；主键为客户端生成的 UUID，本机与云端一致
- 设置分两类：账号设置（默认账户、账期起始日）随账号同步；设备设置（主题、隐私模式、PIN 码）仅保存在本机
- 云端每张表额外带 `user_id`，服务端所有查询按账号隔离（见附录 C）；本机数据库按账号分库，不存 `user_id`

### 8.2 同步协议（概要）

**推送（本机 → 云端）**
- 本机维护 `outbox` 队列：每次新增、修改、删除都记录实体类型与 ID；同一实体的多次修改合并为一条
- 所有变更进入推送队列前有 5 秒缓冲（与撤销窗口一致）；缓冲期内撤销，不产生任何同步记录
- 按「账户 → 分类 → 导入批次 → 记录 → 预算 → 账号设置」的顺序分批 upsert（`onConflict: id`），每批不超过 200 条，成功后出队
- `updated_at` 由数据库触发器统一生成（服务端时间），避免设备时钟不准导致冲突判断错误

**拉取（云端 → 本机）**
- 每张表保存 `lastPulledAt` 游标，请求 `updated_at > lastPulledAt − 5 秒`，按 `updated_at` 升序分页（每页 500 条）
- 游标回看 5 秒，避免并发提交导致漏拉；写入是幂等的，重复拉取没有副作用
- 若某条记录在 outbox 中仍有未推送的本机修改，则暂不覆盖为远端版本，待本机修改推送后以新版本为准

**冲突规则**
- 同一记录被多台设备修改：最后到达服务器的版本生效（Last Write Wins）
- 删除优先：已删除的记录不会被其他设备的修改恢复（由服务端触发器保证）
- 导入批次撤销 = 批量软删除该批次的记录，走同样的删除同步

**首次登录**
- 未登录时产生的本机数据属于「本机模式数据」；登录时按 AUTH-05 处理，选择合并后迁移到该账号的数据库并上传
- 本地主键为 UUID，合并上传不会产生重复记录

## 9. 技术方案建议

仓库现状：Next.js 16 + React 19 + TypeScript，已配置 Biome 与 pnpm，已接入 shadcn/ui 与 Tailwind CSS v4，尚无业务代码。

云端现状：Neon 项目 `cashflow`（`dark-bird-91089133`，`aws-ap-southeast-1`，分支 `production`，数据库 `neondb`），Neon Auth（Managed Better Auth）已在该分支启用，邮箱验证码登录可用；表结构见 `db/migrations/0001_init.sql`，由 `pnpm db:migrate` 通过直连（非 pooled）连接串执行。

> **v0.3 变更**：原方案的 Supabase（Auth + Postgres + RLS + 客户端 SDK）已整体替换为 **Neon + Next.js 服务端**。数据库凭据只存在于服务端，浏览器不再直连数据库，也不再依赖 RLS；鉴权、校验、同步与备份等业务逻辑集中在 `src/server`，通过 `/api/v1/*` 暴露。

| 决策点 | 建议 | 说明 |
|---|---|---|
| 交付形态 | 先做 **PWA**（可添加到主屏幕）；需要上架应用商店时用 Capacitor 封装 | PWA 无需应用商店审核，迭代快 |
| 渲染方式 | Next.js 服务端 + 客户端本地优先；**不能** `output: 'export'` | 业务逻辑与数据库访问在 Route Handlers 里，需要 Node 运行时；页面仍以客户端渲染为主，读本地 IndexedDB |
| 云端后端 | Neon：Lakebase Postgres（业务数据）+ Neon Auth（Managed Better Auth，登录）；权限由 Next 服务端在 SQL 层按 `user_id` 强制 | 不再使用 RLS 与客户端 SDK；服务端连接串不进入浏览器 |
| 客户端 SDK | `@neondatabase/auth`（`createAuthClient()`，只访问同源 `/api/auth/*`）；数据读写走自研 `src/lib/api/client.ts` | 会话在 HttpOnly cookie 中，前端拿不到 token |
| 环境变量 | `DATABASE_URL`（pooled）、`DATABASE_URL_UNPOOLED`（迁移）、`NEON_AUTH_BASE_URL`、`NEON_AUTH_COOKIE_SECRET` | 全部仅服务端使用，`.env.local` 不提交到仓库 |
| 登录 | 邮箱验证码：`emailOtp.sendVerificationOtp` + `signIn.emailOtp`（Neon Auth 托管 Better Auth），不使用 Magic Link | 托管 Auth 自带邮件发送（共享 SMTP），无需接入 Resend/SendGrid；生产环境建议配置自有 SMTP |
| 本地数据库 | IndexedDB（如 Dexie）起步，每个账号一个独立数据库，含 `outbox` 待同步队列 | 浏览器存储可能被系统清理，登录后云端有副本；数据量增长后再评估 SQLite（WASM） |
| 同步 | 自研 outbox + 增量拉取（见 8.2），经 `/api/v1/sync/push` 与 `/api/v1/sync/pull` 落到 Postgres | 服务端逐行 savepoint 写入，单行失败不影响整批；软删除不可被复活 |
| 离线 | Service Worker（如 Serwist）缓存应用壳与静态资源 | 保证断网可用 |
| 图表 | ECharts 或 Recharts（待定） | ECharts 功能全面；Recharts 更轻量 |
| UI 组件 | shadcn/ui（底层 Base UI，`nova` 风格）+ Tailwind CSS v4 | 组件源码在 `src/components/ui`，按需 `shadcn add` 添加；触控元素高度不低于 44px |
| 长列表 | 虚拟列表（如 TanStack Virtual） | 支撑 1 万条记录流畅滚动 |
| 金额 | 整数（分）+ 统一的金额工具函数 | 避免浮点误差 |
| 类型与迁移 | `db/migrations/*.sql` + `scripts/migrate.mjs`（`pnpm db:migrate`，记录于 `schema_migrations`）；手写 `src/server/validation.ts` 的 zod 校验 | 迁移只增不改；不在远程项目里手工改表结构 |
| 测试 | Vitest 覆盖解析器、统计函数与同步逻辑；Playwright 覆盖登录与主流程（可选）；越权用两个测试账号验证（服务端 `user_id` 隔离） | |
| 代码规范 | 沿用已有的 Biome 与 TypeScript 严格模式 | |

## 11. 验收标准

| ID | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 快速记账 | 使用默认账户记一笔支出（输入金额、选择分类、保存）不超过 3 次点击（不含数字输入） |
| AC-02 | 离线 | 开启飞行模式后，可新增、编辑、删除记录；重启后数据完整 |
| AC-03 | 转账 | 转账不影响收入、支出、结余统计，但账户余额正确变化 |
| AC-04 | 导入性能 | 粘贴 500 行合规文本，2 秒内出现预览，导入结果与预览一致 |
| AC-05 | 错误隔离 | 含 5 行错误的文本，有效行全部导入；每个错误行提示行号和原因 |
| AC-06 | 重复导入 | 同一文本导入两次，第二次的记录全部标记为疑似重复并默认跳过 |
| AC-07 | 撤销导入 | 撤销某批次后，该批次记录全部消失，统计与首页即时更新 |
| AC-08 | 统计一致性 | 结余 = 收入 − 支出；分类占比合计为 100%（用固定测试数据验证） |
| AC-09 | 备份恢复 | 导出 JSON → 清空数据 → 恢复，账户、分类、记录的金额与日期逐条一致 |
| AC-10 | 显示适配 | 深色模式与系统字号 200% 下无文字溢出，核心按钮可点击 |
| AC-11 | 登录 | 输入邮箱后收到 6 位验证码，输入正确验证码后进入首页；刷新页面和重启应用后仍保持登录 |
| AC-12 | 数据隔离 | 账号 A 登录后，无法通过任何接口读取或修改账号 B 的记录（用两个测试账号验证 RLS） |
| AC-13 | 多设备同步 | 设备 A 新增一笔记录，设备 B 在前台 10 秒内可见；反向同样成立 |
| AC-14 | 离线同步 | 断网状态下新增 10 笔记录、修改 3 笔，恢复网络后全部上传，云端无重复数据 |
| AC-15 | 冲突 | 两台设备离线分别修改同一记录，联网后只有一条记录，内容为后到达服务器的版本 |
| AC-16 | 删除同步 | 设备 A 删除记录，设备 B 同步后该记录消失；已删除的记录不会被其他设备的修改恢复 |
| AC-17 | 首次登录合并 | 未登录时记录 100 条，登录并选择「合并上传」后，云端新增 100 条；重复执行上传不新增记录 |
| AC-18 | 注销账号 | 注销后，云端该账号的业务数据与登录账号均被删除，本机对应数据被清空 |

### 12.2 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 本机存储可能被系统清理 | 未登录时的本机数据丢失 | 登录后云端有副本，可从云端恢复；未登录时依靠备份提醒与 JSON 导出 |
| Supabase 免费项目可能被暂停；免费计划不提供数据库备份下载 | 云端数据暂时不可用；无法从平台取得备份 | 正式上线前升级付费计划（待确认）；应用内提供 JSON 导出，并提醒定期导出 |
| 账单数据存储在境外云服务（新加坡区域） | 合规与用户信任；国内访问延迟 | 隐私政策告知用户；提供导出与注销；面向中国大陆公开发布前咨询合规意见；实测访问延迟 |
| 国内网络访问 Neon 不稳定 | 同步失败或延迟高 | 本地优先，离线可用；同步状态清晰展示；失败自动重试 |
| 同步冲突导致数据错误 | 金额或分类被覆盖 | 最后写入生效 + 删除优先 + 服务端约束；多设备冲突的自动化测试 |
| 验证码邮件未送达或被当作垃圾邮件 | 无法登录 | 配置自定义 SMTP，并为发信域名设置 SPF、DKIM；内置邮件服务有频率限制，不适合正式使用；自定义 SMTP 下新用户注册的默认上限约为每小时 30 个，大规模推广前需调整 |
| 验证码接口被滥用 | 邮件额度耗尽，产生额外费用 | 60 秒冷却与速率限制；v0.2 上线 CAPTCHA（AUTH-09） |

| 免费项目名额有限（每个账号 2 个活跃免费项目） | 新项目无法创建；恢复被暂停的项目也要占用名额 | 正式环境使用付费计划（待确认）；开发库与其他应用的项目分开规划 |
| 同类产品众多 | 差异化不足 | 聚焦「文本导入 + 分析 + 移动端轻量体验」 |

## 附录 C：数据库结构

> 正式定义见 `db/migrations/0001_init.sql`（v0.3 起由 Neon 托管），迁移通过 `pnpm db:migrate` 执行，不再在文档里维护 SQL 副本。

与 v0.2 草稿的关键差异：

- `user_id` 外键指向 Neon Auth 的 `neon_auth."user"(id)`，`on delete cascade`；用户注销时业务数据随账号一起删除。
- 去掉 RLS 与 `auth.uid()` 默认值：数据库只被 Next 服务端访问，所有查询显式带 `where user_id = $1`。
- `created_at` / `updated_at` 由 `stamp_timestamps` 触发器写入服务端时间；`keep_deleted` 触发器保证软删除不会被后续更新复活。
- `user_settings` 增加 `created_at`，并以 `user_id` 为主键；每张同步表都有 `(user_id, updated_at)` 索引支撑增量拉取。
